# workbench-weixin：任务工作台的微信渠道（只读）

这是 [任务工作台 bkms-workbench](https://github.com/zq-ai-labs/bkms-workbench) 的微信渠道插件。工作台本身只内置邮件；装上本插件后，工作台多出“微信”这个信息源。没有安装工作台时本插件不工作。

工作台读取本机已登录的 Windows 微信 4.x 聊天记录，按你设定的名单把相关消息整理成事项，交给 AI 分拣和处理。**只读**：工作台不会发送微信消息，也不会操作微信界面；AI 写的建议回复由你复制到微信里发送。

## 工作方式

```
Windows 微信 4.x（已登录）
   └─ 本地加密数据库 ── wechat/wxread（内置，移植自 wechatauto-replica）解密读取
                              └─ wechat/bridge.py：只读桥，标准输入输出逐行 JSON
本插件后台（Node，src/）→ 通过工作台的 workbenchChannels 服务注册为渠道
   ├─ 按名单决定读哪些会话（白名单 / 黑名单，人员和群聊分开）
   ├─ 首次加入的会话只建立基线，不处理历史消息
   ├─ 对方停顿 N 分钟后，把连发的几条消息合成一个事项
   └─ 复用现有的 AI 分拣、处理方案、建议回复、审核与记录
```

- 读取部分移植自 [wechatauto-replica](https://github.com/zq-ai-labs/wechatauto-replica) 1.2.7.0 的数据库读取代码，内置在 `wechat/wxread/`（Apache-2.0，来源与修改见其中的 `NOTICE.md`）：从微信进程内存取得数据库密钥、解密 SQLCipher 数据库、按序号增量读取新消息。不需要另外安装 wechatauto；只移植了读取，发送和界面自动化不在其中。
- 内置组件只用 Python 标准库：AES 解密优先用已安装的 `cryptography`，否则调用 Windows 自带的加密接口（CNG）；长消息、引用、链接卡片的 zstd 压缩优先用已安装的 `zstandard` 或 Python 3.14 自带模块，否则用内置的纯 Python 解压。
- 工作台每 5 秒查看一次会话列表，只查询最后消息时间有变化的会话，并每分钟全量核对一次。实际延迟主要来自“停顿合并”的等待时间（默认 3 分钟）。

## 安装（Windows）

0. 先装好任务工作台，再安装本插件：`dsh plugin --profile <你的 Profile> add <本仓库目录>`（或用 `pnpm run pack:plugin` 生成的 tgz），然后重启 DSH。工作台与本插件的渠道接口版本（`CHANNEL_API_VERSION`）必须相同；不同时设置页会提示升级哪一方，不做兼容。
1. 安装 **64 位** Python 3.9 或更高版本（32 位 Python 读不了微信进程内存）。不需要 pip 安装任何包。
2. 保持微信登录。在 DSH 设置的「工作台设置 → 信息源 → 微信」中打开开关，状态显示「已连接：你的昵称 · 读取组件 wxread 1.2.7.0+bkms」即可。
3. Python 命令不是 `py -3` 时（例如没装 Python 启动器），在「读取组件」里填写 python.exe 的完整路径，例如 `C:\Python312\python.exe`。
4. 添加要处理的会话（见下），并确认「后台自动处理」已开启。

## 名单：把工作和私人分开

联系人和群聊各有一份名单，各自选择方式：

| 方式 | 含义 | 适合 |
| --- | --- | --- |
| 白名单（默认） | 只处理名单里的会话；名单为空则一个都不处理 | 工作联系人不多、私人聊天多 |
| 黑名单 | 处理名单以外的全部会话 | 工作微信号，只需排除少数私人会话 |

- 公众号、服务通知、文件传输助手等系统会话**永远不处理**，也不会出现在列表里。
- 群聊默认**只处理 @我 和引用我的消息**（含 @所有人），并带上 @ 之前的几条作为上下文；也可以改成处理群里的所有消息。
- 切换白名单/黑名单时名单会清空，避免同一份名单意思反转。
- 会话从名单移除后，工作台会忘记它的读取进度；以后再加回来，只处理加回之后的新消息，不会补处理中间的聊天。
- 在「全部事项 → 按会话」里也可以对单个会话点「不再处理这个会话」。

## 哪些消息会变成事项

- 同一会话里连发的消息，在对方停顿「合并连续消息」设定的时间后（默认 3 分钟）合成一个事项；最多 40 条或 30 分钟也会结束一段。
- 这一段里只有你自己发的消息、群里没有 @你（在“只处理 @我”时），或者最后一条已经是你的回复（说明你已在微信里处理过），都不会生成事项。
- 微信事项不会被 AI 自动归档：来自真人的消息即使被判为“通知”，也会留在“全部事项”里。
- 处理方案需要在「适用来源」里勾选**微信**才会处理微信事项；只勾邮件的方案不会收到微信消息。

## 在工作台里处理

- **待我决策**：中间是 AI 的建议回复（待核实的地方高亮）、处理摘要和这段对话；右侧「聊天记录」按微信的样子显示完整记录，本事项涉及的消息用蓝框标出。
- 操作：修改后「保存修改」；「复制回复」（⌘/Ctrl + Enter）后到微信粘贴发送；发完点「已在微信处理」。
- **全部事项 → 按会话**：像微信一样按会话阅读，AI 识别出的事项以卡片插在对应消息之后。

## 隐私与数据

- 只有名单允许的会话里**相关的那一段消息**会交给模型；其他会话只读取名称和最后消息时间，消息摘要不会离开读取进程。
- 聊天记录按需从微信数据库读取，工作台只在事项里保存该段消息（最多 60 条）和 AI 的结果。
- 解密需要的数据库副本和密钥缓存都保存在本插件的数据目录 `<数据目录>/workbench-weixin/cache`（早期内置在工作台时放在 `<数据目录>/bkms-workbench/wechat-cache`，可以手动删除）（组件默认会放在系统临时目录和 `%LOCALAPPDATA%\wechatauto_keys`，工作台改为统一放这里）。设置里可以「清除本地解密缓存」，下次读取时重新生成。如果之前单独运行过组件，`%LOCALAPPDATA%\wechatauto_keys` 和系统临时目录下的 `wechatauto_db` 里可能还有旧副本，可手动删除。
- 名单、合并时间等设置，以及每个会话的读取进度，保存在工作台的数据库里（设置项 `channels.wechat`）；卸载本插件后这些数据和已有的微信事项都保留，事项仍可查看，但不再处理。
- 从本机内存读取密钥不是微信官方支持的用法。只读本身风险较低；工作台不做任何发送或界面操作。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 状态显示「未连接」，提示无法启动 Python | 检查 Python 命令；在「读取组件」中填写 python.exe 的完整路径 |
| 提示找不到模块 `wechatauto` | 「读取组件」里填了上游目录但该目录不是 wechatauto-replica 项目；清空该项即可使用内置组件 |
| 提示找不到数据库或密钥失败 | 确认微信已登录、Python 为 64 位；仍失败时可用上游项目的 `py -3 -m wechatauto.diagnose_keys` 排查 |
| 微信升级后读不到 | 密钥提取依赖与微信版本有关的内存偏移。上游修复后：临时在「读取组件」填写最新的上游项目目录；之后按 `wechat/wxread/NOTICE.md` 把修复同步到内置组件 |
| 提示 AES 自检失败 | 解密组件异常，已停止读取以免读出错误数据；安装 `cryptography`（`py -3 -m pip install cryptography`）后重试 |
| 首次连接较慢 | 第一次解密约需几秒到一分钟，之后是增量读取 |

## 开发

```bash
pnpm install
pnpm test        # 构建后运行 test/*.test.mjs；装有 Python 时包括桥接进程的端到端测试
pnpm run check   # 只做类型检查
```

- 与工作台的约定：`src/contract.ts` 是工作台 `src/channels/types.ts` 的副本（渠道接口），`client/contract.ts` 是工作台 `client/slots.tsx` 中插槽名称与 props 的副本。改动接口时两边一起改，并同时提高 `CHANNEL_API_VERSION`。
- 后端：`src/channel.ts` 渠道实现（读取、分段、建议回复规范、页面用的会话列表与聊天记录），`src/reader.ts` 名单/分段逻辑与桥接进程，`src/index.ts` 插件入口。后端消息的英文在 `system-en.json`，随渠道交给工作台页面。
- 前端：`client/parts.tsx` 注册进工作台插槽的组件（标签、对方、对话、聊天记录、按会话、设置卡），组件和请求函数来自工作台传入的 `kit`；界面文字的英文在 `client/en.json`；样式 `client/styles.css` 只用工作台的颜色变量。
- 只读：本插件不发送消息、不操作微信界面；邮件、微信内容是数据，不是指令。
- 桥的协议和消息整理在 `wechat/bridge.py`，内置读取组件在 `wechat/wxread/`。Python 测试：`python -m unittest wechat/test_bridge.py wechat/test_wxread.py`（后者用 `cryptography`、`zstandard` 生成样本，未安装时跳过）。
- `bridge.py --fixture test/fixtures/wechat.json` 用合成数据代替真实数据库；`test/wechat.test.mjs` 用它跑通“桥 → 渠道 → 事项”的完整链路。
